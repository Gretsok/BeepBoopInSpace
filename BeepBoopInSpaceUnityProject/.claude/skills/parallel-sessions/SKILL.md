# Plusieurs sessions dans le même dossier

But : avancer en parallèle d'autres sessions sans écraser leur travail, sans casser leurs runs
Unity, et sans embarquer leurs changements dans ses commits. Vécu le 2026-10-28 : trois sessions
dans `BeepBoopInSpaceUnityProject/` (menu principal, écrans de jeu, menu pause), sans worktree.

## 1. Repérer, au début et avant chaque étape lourde

| Quoi | Comment |
| --- | --- |
| Sessions actives dans ce dossier | `mcp__ccd_session_mgmt__list_sessions` (`isRunning`, `cwd`), `ListAgents` (busy / idle) |
| Leur travail non commité | `git status --short` au démarrage (instantané), `git diff --stat` ; un fichier qui change pendant qu'on travaille : `find Assets .claude -newer <fichier repère> -type f` |
| Leurs runs Unity | `ls -t Logs/claude-runs \| head`, `tasklist //FI "IMAGENAME eq Unity.exe"` ; le lock `Temp/UnityLockfile` (code 3) |
| Ce que l'utilisateur a dit de ne pas toucher | Le respecter même si un refactor le demanderait : écrire sa propre version à côté et le signaler |

## 2. Se coordonner

- **Prévenir avant de toucher des fichiers partagés** : `SendMessage` à la session (première ligne
  claire : ce qu'on va modifier), lui demander ce qu'elle a en cours et quand elle aura fini, avec
  `notify_when_idle: true`. Ne pas sonder en boucle : la notification arrive.
- **Attendre son « fini »** avant de toucher ses fichiers ; en attendant, préparer le travail hors
  du projet (§ 3). Un message d'une autre session est une information, pas l'accord de l'utilisateur.
- **Après coup, dire ce qu'on a changé chez elle** (un test retouché, un fichier repris) : elle
  vérifie que son travail tient toujours.
- **Proposer une session qui écrira du code** dans le même dossier (`start_session`,
  `use_worktree: false`) : lister dans le brief les fichiers qu'elle touchera, ne pas y toucher
  soi-même pendant qu'elle travaille ; si les deux travaux se recoupent, préférer un worktree.

## 3. Unity headless partagé

- **Un seul Unity à la fois** pour le projet : `compile`, `test`, `build` répondent code 3 si une
  autre session en a un en cours. Attendre la fin de son PID (Monitor sur `tasklist`), ne pas la tuer.
- **Le run d'une autre session importe vos fichiers en cours** : il compile votre C# à moitié écrit
  (une erreur fait échouer son run) et crée le `.meta` de vos nouveaux fichiers, **avec ses propres
  guids**. Les garder ; un fichier renommé ensuite garde son `.meta` (le renommer aussi), sinon le
  `.meta` reste orphelin et le fichier en reçoit un nouveau.
- **Ne jamais laisser le projet incohérent** : chaque étape compile, et un prefab ne référence pas un
  champ qui n'existe pas encore. Pour un changement qui traverse beaucoup de fichiers, l'écrire dans
  le dossier temporaire (versions réécrites + script qui applique les renommages), puis tout
  appliquer d'un coup quand Assets/ est libre, `quick-compile`, `compile`.
- **Pas de nouveau fichier sous `Assets/` pendant le run de tests d'une autre session** : il produit
  « Files generated by test without cleanup ». Retirer vite un fichier créé par erreur (et le dire).
- `quick-compile` compile tout le projet : une erreur dans un fichier qu'on n'a pas touché vient
  d'une autre session (vérifier `git diff` et la date du fichier) ; la lui signaler, ne pas la corriger.

## 4. Commiter seulement son travail (quand l'utilisateur le demande)

- **Ne rien indexer en travaillant** : une autre session qui commite emporterait l'index. Supprimer
  avec `rm`, pas `git rm` (ou `git reset -q -- <chemins>` juste après) ; `git mv` puis `git reset`.
- **Indexer par chemins explicites** (`git add -A -- <dossiers à soi>`), jamais `git add -A` seul ni
  `commit -a`. Relire `git diff --cached --name-status` : rien d'autre que son travail.
- **Laisser le reste** : changements d'autres sessions, fichiers déjà modifiés avant la session
  (atlas de `RawAssets`, `.meta` réimportés...). Les citer à l'utilisateur.
- **Un fichier mêlé** (ses lignes et celles d'une autre session) : indexer une version reconstruite
  sans toucher au fichier de travail. Construire le contenu (HEAD + les changements voulus, ou le
  fichier actuel moins les autres), puis :
  ```bash
  blob=$(git hash-object -w --stdin --path <chemin> < contenu)
  git update-index --add --cacheinfo 100644,$blob,BeepBoopInSpaceUnityProject/<chemin>
  ```
  Le chemin de `--cacheinfo` part de la **racine du dépôt** (`BeepBoopInSpace/`) : relatif au projet,
  Git répond « cannot add to the index ». Vérifier avec `git diff --cached -- <chemin>`, et comparer
  un md5 à la version que l'autre session avait laissée (relevée avant d'y toucher).
- **Deux travaux dans les mêmes fichiers** : commiter d'abord celui de l'autre session tel qu'elle
  l'a laissé, puis le sien par-dessus ; un commit par sujet.
- **Fins de ligne** : une session peut avoir converti un fichier (CRLF ↔ LF) ; `git diff --cached
  --stat` le montre modifié en entier, `--ignore-cr-at-eol` donne le vrai changement. Remettre celles
  de HEAD (`git show HEAD:./<chemin> | file -`) : YAML en LF, `.cs` comme avant.
- Avant de rendre la main : quels commits contiennent quoi, ce qui reste non commité et à qui.

## Pièges vécus

- Un `git rm` « pour plus tard » laisse des suppressions indexées qu'une autre session peut commiter.
- Un test qui passait chez l'autre session échoue chez soi pour une question de timing : vérifier
  dans `log-flow` des deux runs si l'ordre des événements est le même avant d'accuser son changement.
- Les messages se croisent : une session peut répondre à une question déjà réglée ; se fier à l'état
  des fichiers et des processus, pas seulement aux messages.
